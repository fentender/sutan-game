## Context

项目为 PySide6 桌面应用（11,272 行 Python + C 扩展），用于合并多 Mod 的 JSON 配置。当前功能完整可用，但存在循环依赖、GUI 与业务逻辑强耦合、God Object/Function、线程安全隐患、缓存失效不可控等结构性问题。

**改造方向**：C++ 基础层 + Python 上层的混合架构。

**关键技术决策**：
- 绑定方式：**nanobind**
- JSON 库：**yyjson**（不可变解析 + 按需可变拷贝，原生支持重复键/注释/尾随逗号）
- JSON 对象采用 **opaque handle 模式**：Python 持有 C++ JSON 对象的引用但不直接读写，所有操作传回 C++ 完成
- 加载时提取常用元数据到 Python 原生类型（方案 B），数据管理模块允许少量 JSON 数据读取
- 缓存策略：GameData 中每个数据项维护 version，缓存基于 version 自动失效

## 一、当前问题全景

### 1. 资源 I/O 散布 & 缓存失效不可控（P0）
- **40 处文件 I/O 散落在 7 个模块**（store.py、parser.py、deployer.py、config.py、loader.py、generator.py、app.py）
- **5 层缓存**手动失效、不级联：`_json_cache` → `_base_data/_mod_data` → `_field_def_cache` → `ModDelta._cache` → `MergeCache._cache`
- 外部文件变更只有 `_json_cache` 通过 mtime 能检测，上层缓存不会自动失效

### 2. 循环依赖（P0）
- `json/store.py` 延迟导入 `merge/cache.py`（第 410、434、459 行）
- 形成 `json → merge → json` 循环

### 3. GUI 严重耦合业务逻辑（P1）
- [app.py](src/gui/app.py)（910 行）直接操作 6 个核心模块
- [diff.py](src/gui/dialogs/diff.py)（888 行）直接操作 `MergeCache`、`JsonStore`
- GUI 无法独立测试业务逻辑，无法复用编排逻辑（CLI / 自动化场景）

### 4. 单例泛滥 & 隐式依赖
- `JsonStore.instance()`、`MergeCache.instance()`、`ModDelta`（类级单例）
- 依赖关系隐藏在实现中，函数签名无法体现

### 5. 线程安全隐患（P1）
- `MergeCache._cache` 无锁、`schema/loader.py` 全局 dict 无锁
- `_field_def_cache` 用 `id(schema)` 作键（GC 后地址复用风险）
- 工作线程和 GUI 线程共享可变状态

### 6. God Object / God Function（P2）
- `JsonStore`（481 行，8 维职责）
- `match_by_heuristic()`（289 行，圈复杂度 ~25）

## 二、C++ 层模块设计

### 总览

```
C++ (libsultan_core)

资源加载模块         （依赖：无）
  └─ 文件 I/O、缓存、mtime 追踪

Json 模块            （依赖：资源加载模块）
  └─ yyjson 解析/序列化、清洗、opaque JsonDoc 对象

JSON 字段操作模块     （依赖：Json 模块）
  └─ 批量字段提取、字段值替换（供 id_remap 使用）

State 模块           （依赖：Json 模块）
  └─ JsonState 类型系列（JsonDictState / JsonArrayState / JsonElementState）
  └─ Json ↔ JsonState 序列化/反序列化
  └─ JsonState → 格式化文本行输出（供 DiffDialog）

Delta 模块           （依赖：Json 模块、State 模块）
  └─ JsonDelta 类型系列（JsonDictDelta / JsonArrayDelta / JsonElementDelta）
  └─ Delta 计算（两个 Json/JsonState 之间的差异）
  └─ Delta 应用（将 JsonDelta 应用到 JsonState）
  └─ Delta 序列化/反序列化（Override 存储）
  └─ Delta 字段过滤（不同合并模式的删除判定）
  └─ 数组匹配算法（四阶段：key→content→similarity→positional）

Schema 查找模块       （依赖：Json 模块）  ※ 后期阶段
  └─ SchemaRegistry、FieldResolver、DslMatcher
  └─ Schema 生成留 Python

诊断模块             （依赖：无）
  └─ C++ 内部 buffer + Python 读取 API
  └─ 关键错误提供回调通知

依赖链：资源加载 → Json → { State, JSON字段操作, Schema查找 } → Delta
                                                                     ↑
                                                     诊断模块（独立，所有模块可调用）
```

### 2.1 资源加载模块

**依赖**：无

负责加载和保存所有文件资源。内部维护缓存，调用方不感知缓存存在。

职责：
- 文件读取（返回原始 bytes/text）
- 文件写入、复制、删除、目录操作
- 缓存管理（mtime 追踪，自动更新）
- 多线程文件批量加载

替代当前：`JsonStore` 的文件 I/O 部分、`deployer.py` 的文件复制、`app.py` 的目录操作。

### 2.2 Json 模块

**依赖**：资源加载模块

将文本/文件解析为 JSON 对象（yyjson），提供 opaque handle 给 Python。

职责：
- 文本 → JsonDoc 解析（yyjson，原生支持注释/尾随逗号/重复键）
- 文件路径 → JsonDoc 解析（通过资源加载模块读取）
- JsonDoc → 文本序列化
- 非标准 JSON 清洗（缺失逗号、BOM 等 yyjson 不覆盖的部分）
- 少量便利查询 API（`get_string` / `get_int` 等，供 Python 提取元数据）

替代当前：`_fast_json.c` 全部 5 个函数、`parser.py` 的 `clean_json_text`/`load_json`/`format_json`/`dump_json`。

### 2.3 JSON 字段操作模块

**依赖**：Json 模块

批量字段提取和修改，供 id_remap 等场景使用。

职责：
- 批量提取 JSON 中某类字段 → 返回字段值数组
- 批量替换 JSON 中匹配条件的字段值（可选原地修改或返回新 JsonDoc）

### 2.4 State 模块

**依赖**：Json 模块

JsonState 描述一个 JSON 文件的变动状态（每个字段标注 ChangeKind：新增/修改/删除/未变）。

类型体系：
- `JsonDictState` — 字典类型的状态
- `JsonArrayState` — 数组类型的状态
- `JsonElementState` — 标量元素的状态
- `ChangeKind` 枚举 — ADDED / MODIFIED / DELETED / UNCHANGED
- `MergeMode` 枚举 — SMART / SIMPLE / WHOLE_FILE_REPLACE

职责：
1. Json ↔ JsonState 双向转换
2. JsonState → 格式化文本行输出：`(left_lines[], right_lines[], change_kinds[])` 供 DiffDialog 展示

### 2.5 Delta 模块

**依赖**：Json 模块、State 模块

JsonDelta 描述两个 JSON 之间的差异变化。

类型体系：
- `JsonDictDelta` — 字典差异
- `JsonArrayDelta` — 数组差异
- `JsonElementDelta` — 标量差异

职责：
1. **Delta 计算**：比较两个 JsonDoc 或两个 JsonState → 产出 JsonDelta
2. **Delta 序列化/反序列化**：JsonDelta ↔ Json（Override 文件存储）
3. **Delta 应用**：将 JsonDelta 应用到 JsonState 上。提供两种模式：
   - 原地修改（性能优先）
   - 返回新 JsonState（安全，保留原状态用于 DiffDialog 中间步骤可视化）
   - 调用方自行选择，也可先 clone 再原地修改
4. **Delta 字段过滤**：删除满足条件的字段（用于 SMART 模式去除 DELETED 字段等）
5. **数组匹配算法**：四阶段匹配（COMMON_MATCH_KEYS 精确匹配 → 内容字段模糊匹配 → 兜底相似度匹配 → 位置对应）

替代当前：`delta.py`、`merger.py`、`array_match.py`、`cache.py`、`formatter.py`、`rules.py`。

### 2.6 Schema 查找模块（后期阶段）

**依赖**：Json 模块

Schema 查找是合并热路径（`get_field_def`），下沉 C++ 避免跨语言调用开销。

职责：
- `SchemaRegistry` — 加载并持有所有 schema，线程安全
- `FieldResolver` — `get_field_def()` 带版本化缓存
- `DslMatcher` — DSL key 模式匹配（正则预编译）

**不下沉**：`generator.py`（Schema 生成留 Python，游戏规则迭代频繁）。

### 2.7 诊断模块

**依赖**：无（所有模块可调用）

- C++ 内部诊断 buffer（warn / error 分级）
- Python 通过 API 拉取诊断信息
- 关键错误提供回调机制实时通知 Python

替代当前：C++ 层内部的诊断需求。Python 层 `diag` 单例仍负责 Python 侧诊断。

## 三、Python 层模块设计

### 总览

```
Python 层

MergeService（GUI 隔离 / 业务编排层）
  ├─→ 数据管理模块（GameData / ConfigData / ImageData / BGMData / OtherData / OverrideData）
  ├─→ 合并管理模块（delta 缓存、合并流程、冲突检测）
  ├─→ id 冲突检测和重分配模块
  ├─→ deployer（部署，通过 C++ 资源加载模块写文件）
  └─→ C++ sultan_core（通过 nanobind）

独立模块：
  config.py（UserConfig）— MergeService 持有引用
  overlap.py（本体重叠检测）— 纯文件层面，不依赖合并
  schema/generator.py（Schema 生成）— 游戏规则迭代频繁
  platform/（steam.py / history.py / updater.py）— 平台集成

GUI 层：
  gui/app.py（MainWindow）— 仅依赖 MergeService
  gui/workers.py（Worker 线程）— 仅包装 MergeService 调用
  gui/dialogs/*、panels/*、widgets/* — 纯展示
```

### 3.1 数据管理模块

管理所有游戏和 Mod 资源数据。

**GameData** 数据结构：
- `type`：游戏本体 / Mod
- `version`：数据版本号（每次数据变更 +1，供缓存失效判断）
- `info.json` 元数据（加载时提取到 Python 原生类型）
- `preview.png` 预览图路径
- `ConfigData`：config/ 目录下所有 JSON 资源的 rel_path → C++ JsonDoc opaque handle 映射
- `ImageData`：image/ 目录下所有图片资源
- `BGMData`：BGM/ 目录下所有音频资源
- `OtherData`：其它资源
- `OverrideData`：该 Mod 的所有 override delta 数据

每个 base 和 mod 对应一个 GameData 实例。支持懒加载（访问时才真正加载资源）。

职责：
1. 初始化：扫描目录构建 GameData（调用 C++ 资源加载模块 + Json 模块）
2. 读取目录 → 返回 GameData
3. 获取 GameData 内各类 id（调用 C++ JSON 字段操作模块）
4. 修改 GameData 内某 id 字段（调用 C++ JSON 字段操作模块，包括文件改名等）
5. 更新 GameData 中某个 JSON 对象内容（传入新文本，C++ 重新解析）
6. 保存 OverrideData（Delta 序列化后写入 override 目录）
7. 允许少量 JSON 数据读取分析（通过 C++ Json 模块的便利查询 API）

非 JSON 资源（图片/BGM）在合并时按 mod 优先级覆盖同名文件，由 deployer 通过资源加载模块执行复制。

### 3.2 合并管理模块

负责 delta 计算、合并执行、冲突检测。

职责：
- 计算各 mod 的 delta（调用 C++ Delta 模块）
- 执行合并（调用 C++ Delta 模块的 apply 功能）
- 维护 delta 和 merge 缓存（基于 GameData.version 判断失效）
- 冲突检测（当前 conflict.py，依赖 Delta 计算结果）

### 3.3 id 冲突检测和重分配模块

C++ 提供查询 API（JSON 字段操作模块的批量提取），Python 做分配决策逻辑，C++ 执行批量替换。

### 3.4 MergeService（GUI 隔离 / 业务编排层）

GUI 的唯一入口。编排 数据管理 + 合并管理 + id_remap + deployer 的完整流程。

```python
class MergeService:
    def __init__(self, config: UserConfig, data_manager: DataManager) -> None: ...

    # 业务流程（每个方法 = 一个完整业务操作）
    def init_project(self, game_path: Path, mod_paths: list[Path]) -> InitResult: ...
    def compute_merge(self, enabled_mods: list[str], progress_cb=None) -> MergeResult: ...
    def deploy(self, output_path: Path) -> DeployResult: ...
    def get_diff_steps(self, rel_path: str) -> list[DiffStep]: ...
    def set_override(self, mod_id: str, rel_path: str, field_path: str, value: str) -> None: ...
    def check_id_conflicts(self) -> list[IdConflict]: ...
    def remap_ids(self, plan: RemapPlan) -> None: ...
    def refresh_mod(self, mod_id: str) -> None: ...
```

规则：
- GUI 不导入任何核心模块，只通过 MergeService
- Service 方法 = 完整业务操作，不是单模块薄包装
- Worker 只包装 Service 调用，不含业务逻辑
- 错误在 Service 内处理，返回结构化结果

## 四、Opaque Handle 与 JSON 边界

Python 持有 C++ JsonDoc 的 opaque 引用，但不直接读写内容。所有操作传回 C++。

```python
# 加载 → 得到 opaque handle
json_doc = json_module.parse(text)          # C++ 返回 JsonDoc 引用
json_doc = json_module.parse_file(path)     # 通过资源加载模块

# Python 不直接操作 json_doc，传回 C++ 处理
state = state_module.from_json(json_doc)    # C++ 构建 State
delta = delta_module.compute(doc_a, doc_b)  # C++ 计算差异
ids = field_ops.extract(json_doc, "id")     # C++ 提取字段 → Python list[str]

# GameData 存储 opaque handle
game_data.config["cards.json"] = json_doc   # Python 管理生命周期
game_data.config["cards.json"].version      # Python 管理版本号

# 少量元数据提取（方案 B）
mod_name = json_module.get_string(info_doc, "name")  # → Python str
```

## 五、缓存策略

不使用全局快照。GameData 中每个数据项维护 version 字段：

```
数据变更 → GameData.item.version += 1
  → 合并管理模块检查 version：与缓存 key 中的 version 不一致则重算
    → delta 缓存 key = (mod_id, rel_path, base_version, mod_version)
    → merge 缓存 key = (rel_path, mod_versions_tuple)
```

- 资源加载模块内部缓存由模块自身管理（mtime 检测），对外透明
- delta / merge 缓存由合并管理模块维护，基于 GameData.version 失效
- Python 层不需要手动 invalidate，version 变更自动触发重算
